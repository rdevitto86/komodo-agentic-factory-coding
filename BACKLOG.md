* **SUB-01.4.9.5 (2026-09-10) — a harness-attested-token approach was tried and found broken, don't re-attempt this exact design.** Built and self-tested (not just proposed): `git_guard.py` stamps a fresh random `KOMODO_APPLY_TOKEN` into every non-reviewer Bash call via `updatedInput` (`export KOMODO_APPLY_TOKEN=<token>; <cmd>`), writes the same value to a state file, and rewrites a reviewer call to `unset KOMODO_APPLY_TOKEN; readonly KOMODO_APPLY_TOKEN; <cmd>`; `comments.py apply` refuses unless the env var matches the state file's current value within a 30s window. Broken by two independent facts, both reproduced live against the actual (now-reverted) code: (1) `readonly` blocks a later shell `export`/assignment-prefix but **not** `env VAR=val cmd`, which builds the child process's environment directly — `env KOMODO_APPLY_TOKEN=<value> python3 comments.py apply` bypasses it entirely; (2) the state file the token lives in is an ordinary, world-readable file at a predictable temp-dir path — `reviewer`'s `Read` tool (never routed through `git_guard.py`'s Bash-only `PreToolUse` hook) reads the current valid token directly, no Bash call needed. Combined: `env KOMODO_APPLY_TOKEN=$(Read the state file) python3 comments.py apply` passes the check with the real token, reproduced end-to-end (`unset ...; readonly ...; env KOMODO_APPLY_TOKEN=<real> python3 comments.py apply` → `comments.py apply` proceeds, exit 0). Root cause, not specific to this implementation: this sandboxed, single-OS-user environment has no channel to carry a secret from one hook invocation forward to a later, independent process's runtime check that isn't *also* reachable through some other unscoped tool (`Read`) or environment-construction primitive (`env`) `reviewer` already has. Reverted via `git stash` (not deleted — recoverable if a future attempt wants to study exactly what broke) rather than committed.
