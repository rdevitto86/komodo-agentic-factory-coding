# Komodo V2: the line is code, the loop is the host

Komodo is rules, roles, standards, skills, a guard, and a small set of deterministic commands that any agent host renders and runs. The host is the factory; Komodo is the line. Moving to another host is one adapter file and one `komodo install --host` call. Nothing outside the adapters knows which host is running.

Status: proposal, 2026-09-21. Replaces the V1 orchestrator. The decisions this reverses are noted in the last section.

## Use cases

| # | Use case | V2 answer |
|---|---|---|
| 1 | Agentic loop over `BACKLOG.md`, rapid iterations, CI-like stages | `komodo tasks` is the line in code; the `run` skill spawns the two model calls; roles are the stations |
| 2 | Ad hoc sessions with Komodo context and standards | `komodo install` renders rules, standards, and roles for every session on the host |
| 3 | Ollama and local models by default, hybrid then fully local | Profiles map tiers to providers; the bridge on Claude Code; Codex with `--oss` for fully local |
| 4 | One config across Claude, GPT, Ollama, and beyond | Source is three neutral formats; one adapter per host |
| 5 | One context and standards set for every Komodo dev and repo | Install is per machine; a repo carries `AGENTS.md`, `BACKLOG.md`, and an optional repo layer |
| 6 | Lightweight hardened guardrails | One guard script, one policy file, one test table run by verify, both hosts |

## Principles

1. **Source is neutral.** `AGENTS.md`, `SKILL.md`, and a role file with frontmatter. Codex and OpenCode read the first two natively; Claude Code reads them through an include. A role renders to an agent definition in about 40 lines.
2. **The line is code; only build and review are model calls.** Picking the wave, assembling a brief, validating a result, rerunning `done_when`, flipping a status, merging a worktree, denying a command: stdlib Python, identical on every host. Building and reviewing: the agent.
3. **The guard is the only enforcement point.** Host permission lists are a convenience layer. The git, destruction, and scope policy holds with hooks alone, because on some hosts that is all there is.
4. **Nothing host-specific outside `adapters/`.** A skill or role never names a host tool, path, flag, or vendor. `komodo doctor` fails on a leak.
5. **No repo config is required.** Defaults in `komodo/config.py`, a per-machine overlay that can only tighten, and an optional committed repo layer. Nothing refuses to run because a file is missing.
6. **Context is budgeted in code.** Always-on under 1500 tokens. Every brief slot has a character cap and a visible cut marker. A session sees standards as one-line pointers; a brief carries the clipped copy.

## Layout

```
komodo/
  AGENTS.md                  universal rules, always on, both hosts read it
  rules/
    accessibility.md         human-facing output contract, included into AGENTS.md at render
    backlog.md               the grammar komodo tasks parses
  roles/<role>.md            frontmatter: tier, tools, session, returns; body: the brief template
  roles/<role>.schema.json   the JSON a worker returns; close validates against it
  skills/
    run/SKILL.md             about ten lines: next, spawn, close, spawn, close, publish
    review/SKILL.md          cold review of a diff in a session
    backlog/SKILL.md         write and refine tasks in the grammar
    standards-<x>/SKILL.md   one per language or domain; trigger by extension
  policy.json                protected refs, forbidden verbs, destructive patterns, prod markers
  hooks/
    guard.py                 PreToolUse on shell, edit, write; reads policy.json and the task scope
    inject.py                SessionStart; prints the repo work state
  adapters/
    claude.py                renders ~/.claude
    codex.py                 renders ~/.codex and ~/.agents
  config.py                  profiles: tier -> provider, model, effort per host; context caps
  tasks.py                   lint, next, done
  line.py                    brief, close, diff, report
  repo.py                    the repo layer: context files, standard overrides, exclusions
  bridge.py                  stdio MCP server over Ollama, standard library
  run.py                     the headless launcher
  comments.py                the comment lint
  doctor.py                  references, portability, drift
  cli.py                     install | doctor | tasks | comments | guard | bridge | run
tests/
scripts/verify.py
templates/project/           AGENTS.md, BACKLOG.md, CHANGELOG.md for a new repo
```

Target size: about 1400 lines of Python. V1 is 4933 plus 1013 of Go.

## The assembly line

Every station but two is a `komodo tasks` command. The `run` skill is the list of those commands and the two spawns, so the session judges only what to spawn and what a result says.

| Station | Who | What |
|---|---|---|
| Intake | `tasks next --json` | The next READY group: tasks, dependencies, waves by directory, type, version. Tasks with a valid result on disk are skipped, which is resume |
| Brief | `tasks brief <task>` | Fills the role template from the slots below, writes the brief and the scope file, creates the worktree |
| Build | builder role, spawned by the skill, one per task in the wave | Reads its brief path; owns the scope; writes its result JSON |
| Close | `tasks close <task>` | Validates the result against the role schema, reruns `done_when`, runs the comment lint, flips the status. A failure writes the failure slot and the previous diff for one repair brief |
| Wave | `tasks close --wave` | Merges the wave's worktrees in order and stops on conflict; runs the repo's verify |
| Review | reviewer role, spawned by the skill, fresh context | Reads only `tasks diff`; on another tier or vendor when the profile says so. One pass per group, one repair |
| Publish | `tasks close --group` | Commit on `<type>/<name>`, push, PR, changelog line, status DONE |
| Report | `tasks report` | Per-task seconds, turns, tokens when the host reports them, findings; in the accessibility format |

Headless: `komodo run <group>` scrubs push credentials, picks the host from the profile, and runs the host's non-interactive mode with the `run` skill and the group id.

### Why this will not repeat 0.x

The 0.x loop was 200 lines of prose the session interpreted: nine gates, three to four reviewer forks per band, verify on every Stop, 7k tokens re-read after every compaction. Here the prose is about ten lines under 800 tokens, every gate is a command, review is one pass, verify runs once per wave, and worktrees and parallel agents are host features. TG-03.5 runs one group under V1 and V2 and records wall time and tokens; slower by more than a wave means the skill is wrong.

## Context injection

`tasks brief` fills the builder template with the slots V1 filled, each capped in `config.py` with the head-and-tail clip and a visible marker:

| Slot | Source | Default cap |
|---|---|---|
| task block | the task's YAML | none |
| repo rules | the repo's `AGENTS.md`, or a one-line default | 8k chars |
| repo context | `.komodo/context/*.md` whose globs match the task's files | 8k chars |
| context | the task's `context` anchors, resolved to sections | 10k per file, 24k total |
| files | the task's `files`, existing ones read | 10k per file, 24k total |
| standards | by extension and role, from the skills directory plus the repo layer | 6k per standard |
| done when | the task's commands | none |
| failure | the failed command output and the previous attempt's diff, on repair only | 80k |

The reviewer's brief carries the diff, the group's tasks, and the standards the diff touches. A session agent gets none of this by injection; it gets the same rules always on and the same standards by trigger.

## The repo layer

A repo may commit a `.komodo/` directory. Nothing in it is required, a malformed file is skipped with one line in the report, and it never widens what the machine floor allows.

- **`.komodo/context/*.md`**: repo knowledge with a `paths:` glob list in frontmatter. A file whose globs match a task's files is injected as repo context. No globs means every task.
- **`.komodo/standards/<name>.md`**: extends a shipped standard of the same name, or adds one the toolkit never shipped, with the same frontmatter trigger.
- **`.komodo/exclude`**: shipped standards this repo never loads, with a floor of comments, api-security, and sdlc it cannot reach. `komodo doctor` fails when an excluded standard's extensions still match tracked files and no override exists.
- **Precedence**: `config.py` defaults, then `~/.komodo/config.json` which can only tighten caps and add denials, then the repo layer.

## Roles

A role file is the brief. Frontmatter declares what the adapter needs; the body is the template `tasks brief` fills.

```markdown
---
name: builder
tier: standard          # light | standard | heavy; a profile maps it
tools: [read, edit, write, shell, search]
session: true           # also rendered as a session agent
returns: builder.schema.json
---
You are a builder. You own exactly the files under Scope. ...
# Task {{task_block}}
# Repo rules {{repo_rules}}
# Repo context {{repo_context}}
# Context {{context}}
# Files {{files}}
# Standards {{standards}}
# Done when {{done_when}}
{{failure}}
```

Tool names are Komodo's five verbs; the adapter maps them to the host's tool names.

## Profiles and local models

A profile maps each tier to a provider, a model, and an effort, per host. The role never names a model.

| Profile | Host | light | standard | heavy | reviewer |
|---|---|---|---|---|---|
| `claude` (default) | Claude Code | haiku | sonnet | opus | opus |
| `hybrid` | Claude Code | ollama via bridge | sonnet | opus | opus, or ollama |
| `codex` | Codex | small | standard | large | large |
| `local` | Codex `--oss` | small local | coder local | coder local | coder local |

Model names are placeholders the config verifies at install time; role and skill files never carry them.

On Claude Code a subagent cannot run on Ollama. A light role in the `hybrid` profile calls the bridge from its body: `komodo bridge` is a stdio MCP server in the standard library that the host spawns, so there is no process to keep alive and nothing to install beyond Ollama. The reviewer tier may also point at Ollama, so a review never shares a vendor with the build. On Codex the `local` profile sets Ollama as the provider and every tier runs locally.

## The non-proprietary day

Both Komodo devs run Claude Code today. The plan assumes a day when the host is something Anthropic does not own, and is built so that day costs one adapter file:

- **Nothing outside `adapters/` names a vendor, a host tool, a host path, or a host flag.** `komodo doctor` fails on a leak.
- **The three source formats are open.** `AGENTS.md` and `SKILL.md` are read natively by Codex, OpenCode, and others; a role renders to any of them.
- **Codex is the rehearsal, not the destination.** Its CLI is open source and its surfaces match Claude Code one for one, so it proves the source is neutral with the least work. OpenCode, Goose, or whatever wins later is a third adapter under the same source.
- **The exit test:** `komodo install --host <new>` with zero changes outside `adapters/`, then one group through the launcher. TG-03.8 runs that test once, under Codex.
- **Subscriptions do not travel.** Since April 2026 a Claude subscription covers only Anthropic's own apps. Any other host bills an API or runs locally; the `local` profile is the answer that costs nothing.

## Guardrails

One script, the guard, on every host's PreToolUse for shell, edit, and write. It reads `policy.json` and, in a worktree, the task scope `tasks brief` wrote.

Denied:
- **Git**: push, commit, merge, or delete on a protected ref; force; amend; rebase; reset; checkout; restore; any co-author or generated-by trailer.
- **Destruction**: recursive delete outside the worktree, `DROP DATABASE`, `TRUNCATE`, `terraform destroy`, `kubectl delete namespace`, cloud delete verbs, and any command naming a host in the prod markers.
- **Scope**: an edit or write outside the task's `files` when a scope file exists.

Behaviour: deny only on a finding. An internal error is logged to stderr and allowed, because a guard that fails closed stalls every command on one bug. The cost of fail-open is bounded by `komodo guard check`, which runs a table of at least 60 commands inside verify, so a broken guard fails the gate and never a run.

Credentials: the headless launcher strips push tokens, credential helpers, and SSH identities, which is V1's structural guarantee for unattended runs. In an interactive session the guard is the gate, and a dev's own terminal is the dev's own.

## Distribution

Every Komodo dev clones this repo and runs one command:

```
python3 -m komodo install --host claude    # or --host codex, or both
```

Install renders into the home directory only. `komodo doctor` reports drift between the rendered layout and the source, and a broken reference in any rule, role, or skill. A repo starts from `templates/project/`.

| Removed | Replaced by |
|---|---|
| `pipeline.py`, `dag.py`, `state.py`, `gates.py`, `pr.py`, `pr_actions.py` | `komodo tasks` and the `run` skill |
| `workers/`, `briefs/`, `briefs.py`, `render.py` | role files, `tasks brief`, and the adapters |
| `account.py`, plan detection, rate windows | the host's own limits |
| `gitops.py` | `policy.json` read by the guard; the launcher's credential scrub; `tasks close --group` under the guard |
| `hooks/src`, `hooks/bin`, pre-commit, pre-push | the two hook scripts under `komodo/hooks` |
| `standards.py` and the standards render | standards as skills at the source; the repo layer module |
| Windows port, install drift groups, the V1 backlog | dropped |

Decisions this reverses in `docs/design-decisions.md`: "The pipeline is code, not a prose state machine" becomes "The line is code, the loop is the host", and "Guarantees are credential isolation plus one pusher" becomes "Guarantees are the guard, the launcher's scrub, and verify". TG-03.9 rewrites both.
