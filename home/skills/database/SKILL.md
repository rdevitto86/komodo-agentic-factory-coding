# Database

Engine-agnostic rules first, then what changes per engine. Generic hygiene — parameterised queries, no `SELECT *`, `NOT NULL` by default, bounded result sets — is assumed and not restated.

**Read the repo before assuming an engine.** The dependency manifest and the migrations directory say which one is in use; more than one may be.

## Comment discipline

`comment-rules` carries the shared template contract. `.sql` has no engine-specific machine directive in the guard's list — every comment is judged only against the generic templates (banner, `WHY:`/`NOTE:`/`FIXME:`/`HACK:`, `TODO(user):`, indented step marker). A comment describing what a query does prompts for approval like any other narrative comment.

## Universal rules

### Naming

- **Tables and collections**: plural `snake_case`. Junction tables combine both names alphabetically. No `tbl_` prefixes.
- **Fields**: `snake_case`, spelled out — `description`, not `desc`. Booleans take `is_` / `has_`. Foreign keys are `<referenced_singular>_id`.

### Keys

- **UUID primary keys**, generated by the database where the engine can. Composite keys only for pure junction tables or a deliberate partition/sort design.
- **Never expose sequential integer IDs externally** — enumeration risk. If the engine issues one internally, it stays internal.

### Timestamps

`created_at`, `updated_at`, and `deleted_at` on anything with a lifecycle, always timezone-aware UTC. **`created_at` comes from the database, never the application clock** — the app's clock is a different machine's opinion. `updated_at` updates on every write.

### Migrations

- **Every schema change is a migration.** No manual edits in any environment; application code never builds schema.
- **Files are immutable once merged.** Name them `<sequence>_<description>` with a forward and a reversing file.
- **Every forward migration has a tested reverse.**
- **Never lock a large table.** Add the column nullable, backfill separately, then constrain.

### Soft deletes

Use a nullable `deleted_at` when history matters, the record may be referenced, or a delete may need undoing. **Every read filters it**, backed by an index that covers the filter. Hard-delete only ephemeral data or a regulatory erasure — tombstone first.

### Security

- **Least-privilege users, no DDL in production.** Separate read and write identities for read-heavy workloads.
- **Credentials live in a secrets manager**, never in source or a plain environment variable.
- **TLS everywhere outside local.**
- **Audit access to payment and PII tables** where the engine supports it.

## Relational engines

**Index every foreign key.** Most engines do not do it for you, and the missing index surfaces as a slow delete on the parent, not a slow read.

**Partial indexes for the soft-delete filter** where supported — indexing rows already excluded from every query is wasted write cost.

**Enforce uniqueness in the database** with a unique index, not only in the application. Two application instances race; the index does not.

**Measure before adding an index.** Run the engine's query planner on the real shape and confirm the index is chosen. No speculative indexes — each one is a write-time tax paid forever.

**Foreign keys are declared**, not implied by convention, wherever the engine enforces them.

## Document and key-value engines

**Access pattern first, then schema.** The query you will run determines the key design; designing the entity first and querying it later is how these engines become expensive.

**Single-table design for entities accessed together.** A join you cannot make is a second round trip.

**The partition key must distribute load.** A key with few distinct values, or one skewed toward a popular tenant, creates a hot partition that throttles independently of total capacity.

**Sort keys are for intentional range queries**, not for storing a second attribute.

**No joins — denormalise and accept write duplication.** Then own the consequence: every copy needs an update path, and that path is application code with no transactional guarantee behind it unless you buy one.

**Secondary indexes and transactions are expensive.** Use them deliberately, and know which of read cost, write cost, or both each one adds.

**TTL for anything ephemeral.** Expiry is cheaper than a scheduled delete job.

## Embedded engines

**Concurrency is the constraint, not size.** An embedded database typically serialises writers; a design assuming a connection pool of writers will serialise or fail under load. Check the engine's locking mode before choosing it for anything multi-writer.

**Type affinity is weaker than a server engine's.** Validate at the application boundary rather than trusting the column type to reject bad input.

**The file is the deployment unit.** Back it up, version it, and treat its location as configuration — not a hardcoded path.

**Migrations still apply.** Being a single file is not a reason to mutate schema by hand.
